# Персональный AI-помощник в Telegram

Python/FastAPI/PostgreSQL с pgvector, сменным AI adapter и очередями в БД. Telegram использует long polling. Agent runtime сохраняет историю и результаты инструментов, контролирует операции и стоимость AI. Поручения, approvals, долговременная память и текстовые PDF работают через доменные обработчики. Незарегистрированные возможности не предлагаются модели.

## Локальный запуск

Требуются Docker и Compose v2. Скопируйте `.env.example` в локальный `.env`, задайте случайный `SERVICE_TOKEN`, пароль PostgreSQL и согласуйте его с `DATABASE_URL`. Укажите разрешённый Telegram ID, Telegram-токен, `AI_API_KEY` и `AI_FOLDER_ID`. Секреты передаются окружением и не входят в Git.

```sh
cp .env.example .env
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8000/health
```

Backend применяет Alembic migrations перед запуском. Четыре сервиса имеют restart policy и health checks. PostgreSQL и файлы имеют постоянные volumes. Без AI/Telegram credentials каркас поднимается для проверки инфраструктуры, но не является доступным демонстрационным ботом. По умолчанию часовой пояс `Europe/Moscow`; относительные даты привязаны к времени исходного Telegram-сообщения, чтобы очередь после простоя не сдвигала намерение пользователя.

## AI и стоимость

Generation: `gpt://<folder>/deepseek-v4-flash`, Yandex OpenAI-compatible API `https://ai.api.cloud.yandex.net/v1`, заголовки `Api-Key` и `OpenAI-Project`. Embeddings: `emb://<folder>/text-embeddings-v2-doc/` и `text-embeddings-v2-query/`, запрашивается 256 измерений. Невалидный/нечисловой вектор отклоняется.

`TOOL_PROTOCOL=native` включает native tool calling с сохранением `tool_call_id`. `TOOL_PROTOCOL=json` явно выбирает строгий JSON-протокол `final{text}` либо `tool{name,arguments}`. Режим не переключается автоматически при ошибках сети, квот или авторизации. Локальные тесты используют тестовый transport; production не имеет поддельных ответов.

После настройки окружения и migrations выполните безопасную проверку:

```sh
docker compose exec backend python -m scripts.probe_ai
```

Probe выполняет безвредный echo tool roundtrip и doc/query embeddings, сохраняет метрики в БД и выводит статус с идентификатором операции без запросов/секретов. Если native tools действительно не поддерживаются, зафиксируйте ошибку и явно выберите JSON mode, затем повторите проверку. Live proof 2026-10-04: DeepSeek V4.1 Flash в native mode прошёл настоящий tool roundtrip, оба embeddings вернули 256 значений. Gateway embeddings требует явную версию `/latest`; adapter добавляет её к URI с пустой версией и запрашивает float. Generation gateway возвращает `gpt://deepseek-v4.1-flash/latest` без folder ID; pricing alias хранится в конфигурации. Владелец настроил V4.1 Flash через environment; исходная V4 Flash также остаётся доступной конфигурацией.

Каждая HTTP-попытка AI имеет собственную строку `ai_calls`: provider/model/type/scenario, nullable фактические токены, numeric usage details, latency, status/error, логический call ID, attempt, стоимость/полнота/валюта/версия и snapshot ставок. Начатая до сбоя попытка остаётся с неизвестным исходом. Retries считаются отдельными попытками; каждый generation request расходует общий бюджет операции. Для безопасности многоязычного контекста используется консервативная оценка по UTF-8 bytes полной сериализации запроса с запасом. Лимиты: суммарный вход 16 000, выход 2 000 на вызов, максимум пять индивидуальных вызовов инструментов, включая некорректные. Перед финальным ответом инструменты отключаются.

Ставки находятся в `config/pricing.json`, а не в доменной логике. Снимок на 2026-10-04: DeepSeek вход 0,30 ₽/1000, cache 0,075 ₽/1000, выход 0,50 ₽/1000; embeddings 0,0101 ₽/1000. Cache является частью входа, reasoning — частью выхода; результаты пользовательских функций оплачиваются как обычный вход. Embedding prompt/total учитывается один раз. Если применимая метрика неизвестна, стоимость отмечается неполной; отсутствие usage не превращается в нулевое потребление. [Тарифы Yandex](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing), [embeddings](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/embeddings).

`GET /internal/operations/{id}/usage` возвращает сумму известной стоимости, количество неполных вызовов и известные токены с количеством неизвестных значений. Результаты реальных четырёх сценариев приведены ниже; технический отчёт содержит все попытки, включая unknown показатели. Для PDF измеряются отдельно индексация и вопрос. Тестовые показатели не являются экономикой живой демонстрации.

## Внутренние контракты

Все `/internal/*` требуют `Authorization: Bearer <SERVICE_TOKEN>`. `POST /internal/updates` сохраняет update, операцию и job одной транзакцией до ответа; `update_id` уникален. Чужие updates игнорируются. Long polling продвигает сохранённый checkpoint только после durable ingress. Callback и document metadata также сохраняются. Данные и история привязаны к владельцу; смена разрешённого ID открывает отдельную историю, очереди старого владельца не обрабатываются.

`Registry` предоставляет только реально зарегистрированные `create_task`, `prepare_meeting`, `save_memory`, `search_memory`, `search_document`, `prepare_data_deletion`. Обработчик объявляет Pydantic arguments (рекомендуется `extra=forbid`), `prepare(ctx,args)` для AI/IO вне транзакции и `apply(session,ctx,args,prepared)` для атомарного изменения домена и сохранения результата invocation. Context содержит владельца, chat/operation IDs, reference UTC, timezone, idempotency key и source update. `ToolResult` имеет `status` (`ok`, `needs_clarification`, `error`), `data`, `user_message`, `buttons`, `sources`. Для результата с approval buttons обязательный `user_message` содержит каноническое описание из immutable payload; пользователю отправляется оно, а не пересказ модели. Callback, uploads и виды фоновых jobs подключаются отдельными hooks.

Полный результат сохраняется в invocation; модель получает сокращённую проекцию, рассчитанную под оставшийся бюджет финального запроса. Все пять источников и поля document ID/name/page/chunk ID сохраняются; сокращаются только excerpts и текстовые данные, с флагом truncation. Необходимые метаданные, которые не помещаются, приводят к понятной ошибке лимита. После рестарта завершённый invocation не выполняет доменную запись повторно.

Jobs/outbox используют PostgreSQL `SKIP LOCKED`, lease 120 секунд и уникальные ключи. Background worker обновляет lease каждые 15 секунд; stale token не может фиксировать результат. Операции одного владельца обрабатываются последовательно; DB-транзакция не удерживается во время AI. Outbox разбивает plain text по 4000 UTF-16 units и повторяет отправку после ошибок. Если Telegram принял сообщение, а процесс упал до ack, возможна повторная отправка. Это окно внешней доставки не даёт повторных доменных действий. Логи содержат job IDs и классы ошибок; тексты provider exceptions и URL Telegram с токеном не выводятся.

## Поручения и подтверждения

LLM извлекает структурированную дату с исходной подстрокой: абсолютная локальная дата/время, точный интервал, ближайший будущий день недели или вопрос для уточнения. Backend рассчитывает срок относительно сохранённого времени сообщения и `TIMEZONE`. «Завтра в 15:00», «в пятницу в 10:00» и «через два часа» не требуют подтверждения. «Вечером», «после обеда» и «через несколько дней» требуют точности; выдуманная моделью дата не обходит этот контроль.

Создание поручения и неизменяемого approval сопровождается каноническим сообщением из backend, сохранённым вместе с результатом даже при сбое последующего AI-вызова. Если модель отметила `complete_request=true` и операция содержит ровно один встроенный вызов `create_task` или `prepare_meeting`, готовый результат завершает запрос без проекции и дополнительной генерации. Признак означает, что действие отвечает на все части просьбы; по умолчанию он выключен. Смешанные запросы продолжают общий agent loop. После перезапуска используется сохранённый результат и тот же ключ доставки. Встреча остаётся pending до кнопки владельца, подтверждение действительно 24 часа. Отмена и истечение срока не выполняют действие. При подтверждении атомарно сохраняются approved_at и simulated/executed_at; реальный календарь не используется.

Scheduler работает отдельной coroutine каждые пять секунд, независимо от ожидания AI; Telegram long polling имеет server timeout 25 секунд; получение updates, отправка ответов и typing работают независимо через постоянные HTTP clients. Connect timeout — пять секунд, исходящие отправки — десять секунд. Сроки и сообщения сохраняются в PostgreSQL. Просроченное поручение ставится в исходящую очередь с указанием задержки; уникальный ключ исключает повторную постановку напоминания. После отправки всё ещё возможно документированное окно повторной Telegram-доставки до ack.

## Обратная связь и управление данными

После приёма запроса Telegram показывает typing; worker поддерживает его каждые четыре
секунды до фактического подтверждения доставки всех частей ответа либо конечного
отказа доставки. PDF получает одно короткое сообщение о приёме и обработке.
Для обычного запроса, который продолжается дольше десяти секунд, появляется один
progress. Сообщения подтверждают работу без названий внутренних компонентов.
Сетевая недоступность Telegram может задержать получение или показ обратной связи.

- `/memory` или «Что ты сейчас обо мне помнишь?» — сохранённые записи текущего
  пользователя напрямую, без generation/embedding. Страницы по 20 записей,
  длинные записи явно сокращаются; версии фактов сохраняются. Обычный смысловой
  вопрос к памяти продолжает использовать AI.
- `/clear_memory` — подготовить очистку долговременной памяти.
- `/delete_documents` — подготовить удаление документов пользователя и их содержимого.
- `/reset` — подготовить полный сброс пользовательских данных для новой демонстрации.

Три команды удаления только показывают карточку: точный снимок на момент подготовки,
количества объектов, необратимость, оставшиеся данные и кнопки «Подтвердить»/«Отменить».
Подтверждение действительно 24 часа и проверяется по владельцу и чату; повторная кнопка
не выполняет удаление заново. Новые данные из запросов после подготовки сохраняются.
При частичной очистке несвязанные поручения и встречи остаются; прежний контекст
диалога очищается. Full reset удаляет также старые поручения, напоминания и встречи.
Минимальные записи подтверждения/защиты от повтора и числовые метрики сохраняются без
исходного содержимого. Уже отправленные сообщения Telegram и данные внешних сервисов
этими командами не удаляются.

Удаление файлов выполняется по сохранённому плану с повторами после сбоя. Старые
записи/задачи не могут восстановить удалённые данные. Состояние удаления становится
`executed` после отсутствия управляемых файлов; до этого `executing`. Это логическое
удаление файлов, не обещание физического стирания носителя.

Latency доступна через service-auth API `/internal/operations/<id>/latency`:
`source_to_ingress_ms`, `queue_wait_ms`, `runtime_ms`, `retrieval_ms`, `ai_ms`,
`llm_tool_loop_ms`, `delivery_ms`, `end_to_end_ms`, `source_to_ack_ms` и временные отметки фактического
feedback/final ack. Telegram source time имеет точность одну секунду; время backend
приёма хранится отдельно. Старые неизвестные отметки, pending/failed доставка остаются
nullable. AI и retrieval входят в runtime: длительности нельзя просто складывать.
Для ответа из нескольких частей final ack требует фактической отправки всех частей;
progress и будущие напоминания не считаются финальной доставкой этого запроса.

Измерения на bigbang, 2026-10-04, executable `d39e998`: три одинаковых запроса
«Что ты сейчас обо мне помнишь?» доставлены за 1,705 / 0,935 / 0,787 с после приёма
backend, против 8,587 / 23,910 / 6,628 с на предыдущем образе. Первый typing
подтверждён через 0,484 / 0,344 / 0,373 с. Обзор использует **0 AI-вызовов и 0 ₽ AI**;
контрольный смысловой поиск с настоящим provider и проверенным источником — 5,527 с.
Сопоставимые запросы поступали через внутренний API; отправка ответов была настоящей
Telegram. Они измеряют ingress → фактический ack и не включают получение из Telegram;
три наблюдения не задают SLA. Исходная минутная задержка включала 45,120 с до backend
при ConnectTimeout, а AI занял 4,634 с. Внешний маршрут Telegram остаётся ограничением.

Доставка канонического ответа иногда завершается до окончания AI loop: интервалы
перекрываются, `delivery_ms` после processing тогда неприменим (`null`), а e2e остаётся
временем фактической доставки всех частей. Progress и напоминания в него не входят.
[До](docs/measurements/2026-10-04-ux-latency-before.json),
[после](docs/measurements/2026-10-04-ux-latency-after.json),
[живой PDF progress](docs/measurements/2026-10-04-ux-feedback.json).

Доработка и результаты приёмки: [URALBYTE-8](docs/followups/URALBYTE-8.md).

Исправление [URALBYTE-9](docs/followups/URALBYTE-9.md) проходит отдельную проверку;
до повторной проверки конфликта демонстрация заказчику заблокирована.
Checker source PASS и Reviewer APPROVE получены для исправления границ субъектов
составных записей. Исправление опубликовано в [PR3](https://github.com/ural-byte/5523789-chief-ai-assistant/pull/3):
CI проверенного source commit прошёл, новый образ развёрнут в bigbang. Старая зависшая
операция получила один конечный ответ с реальным Telegram ACK без повторного AI/tools;
обе записи сохранены. [Результаты поставки](docs/deployment/bigbang-uralbyte9.md).
Настоящий вопрос → выбор → карточка → подтверждение владельца → повторный вопрос
ещё ожидается; до его проверки демонстрация остаётся заблокированной.
Обычные операции имеют сохраняемый предел обработки 90 секунд от приёма, PDF —
15 минут. Итог — успех, уточнение, ожидание подтверждения, отмена либо понятная ошибка:
«Не удалось завершить обработку или доставить ответ. Проверьте результат действия
перед повторным запросом.»
Зависший executor прерывается независимо; просроченные результаты не выполняют
инструменты повторно. Scheduler и уже подтверждённая уборка работают независимо.
Пустой или состоящий из пробелов ответ не считается успехом.

Доставка ограничена 60 секундами и четырьмя попытками; постоянная ошибка Telegram
не вызывает бесконечных повторов. Для сбоя допустим один отдельный конечный ответ
с собственным ограниченным бюджетом, без повторения доменных действий. Если Telegram
недоступен и этот ответ доставить невозможно, сохраняется `delivery_failed`, typing
прекращается; фактический ACK не подменяется. Пределы служат защитой от зависания,
а не обещанием времени ответа. Известное окно возможной повторной доставки сохраняется.

Исправление выбора актуальной версии [URALBYTE-11](docs/followups/URALBYTE-11.md)
получило независимые Checker PASS (613 тестов, 109 дополнительных проверок,
4 реальных Yandex сценария) и Reviewer APPROVE. [PR5](https://github.com/ural-byte/5523789-chief-ai-assistant/pull/5):

и approvals сохранились. [Поставка](docs/deployment/bigbang-uralbyte11.md).
Полный сценарий с настоящим подтверждением владельца в Telegram ещё ожидается;
клиентская приёмка PENDING, демонстрация BLOCKED до этой проверки.

«Запомни: Иванов отвечает за бюджет» сохраняет исходное сообщение и embedding, а сущности/факты — в отдельных таблицах. LLM определяет явное намерение сохранить из текущего сообщения, включая просьбу после приветствия или контекста; позиционный regex/keyword gate отсутствует. Рассказ без просьбы, отрицание и обсуждение цитаты не считаются просьбой сохранить. Backend валидирует аргументы, владельца, разрешённый инструмент, идемпотентность и deadline; source сохраняется из исходного Update. Фактический результат save_memory возвращается модели, которая готовит итоговый ответ; отдельное раннее canonical подтверждение сохранения не отправляется. Новая версия факта не перезаписывает старую; поиск возвращает все версии релевантного факта, а backend добавляет понятное сообщение с полным содержанием обеих противоречащих записей, даже если модель их пропустила. Память, факты, документы и поиск изолированы по Telegram user ID.

После ответа с конфликтом ясный выбор, например «Лёша — правильный вариант»,
сразу создаёт карточку удаления другой версии. Backend сопоставляет выбор с
доставленной структурированной парой и атомарно сохраняет keep/delete и конкретный
approval_id. Pending approval — сохранённое состояние awaiting_approval; его
неизменяемый payload фиксирует choice_recorded. Повторное «да», «удалить» или «a»
возвращает ту же карточку без LLM, поиска и повторного выбора, даже после рестарта
или обрезки истории. Смысловой выбор через инструмент также заканчивается готовой
карточкой без дополнительной генерации. Карточка содержит точные тексты обеих
записей и предупреждение о необратимости. До нажатия кнопки память сохраняется;
текстовое подтверждение не удаляет данные. Callback содержит конкретный approval_id
и проверяет владельца, чат, 24-часовой срок и неизменность обеих записей. Повторное
нажатие не выполняет удаление заново. Неоднозначный первоначальный выбор требует
уточнения; записанный выбор больше не переводится к вопросу об актуальной версии.
После удаления устаревшая версия не участвует в поиске и не восстанавливается
из прежнего контекста. Несвязанные и новые данные сохраняются.
Выборочное разрешение пока ограничено безопасно разделимыми одиночными утверждениями
о руководителе явно названной организации, команды или подразделения. Backend
сверяет полные записи, факты и действительно доставленную конфликтующую пару.
В структурированной паре имя берётся из сохранённого значения факта; словарь имён
не определяет намерение пользователя. Составные записи с независимыми фактами и
неоднозначные пары требуют уточнения. Пользовательские тексты показывают содержание
версий без UUID, внутренних ссылок и диагностического представления памяти.

Пришлите текстовый PDF до 10 МБ/100 страниц. Worker скачивает файл потоком с ограничением размера; backend публикует файл с UUID-именем в постоянном volume. pypdf извлекает текст вне event loop; фрагменты до 2000 символов с перекрытием 200 сохраняются по страницам. Повтор загрузки не создаёт второй документ; после рестарта индексация пропускает сохранённые фрагменты. Незавершённый или ошибочный индекс не участвует в поиске. PDF без текстового слоя требует OCR, который прототип не поддерживает. После ошибки можно повторно прислать исправленный файл.

При нескольких PDF агент запрашивает имя или ID. Поиск выбирает пять фрагментов одного документа. Следующий AI-вызов выполняется без инструментов и возвращает ответ с идентификаторами источников. Backend проверяет принадлежность всех ссылок найденным фрагментам и добавляет название/страницы. При отсутствии оснований либо некорректных ссылках выводится понятное сообщение. Инструкции внутри PDF рассматриваются как данные и не разрешают новые действия. Проверка ссылок подтверждает происхождение цитат; смысловая корректность ответа дополнительно проверяется в живой демонстрации.

Неуспешные диагностические прогоны хранятся отдельно в БД и не выдаются за этот успешный прогон.

После успешного probe запустите (команда создаёт настоящие поручение, память и pending
approval в текущем аккаунте; встречу автоматически не подтверждает):

```sh
docker compose exec backend python -m scripts.benchmark \
  --output /srv/data/documents/benchmarks/demo --revision <git-commit>
docker compose cp backend:/srv/data/documents/benchmarks/demo ./demo-measurements
```

Background должен работать. Измерение проходит через ingress, file API и agent loop;
PDF — небольшой настоящий текстовый fixture, ответы получает настоящий API. Для локального
PDF-transfer используется service-auth header `X-Local-Upload: true`, который сохраняет
update/операцию и откладывает getFile до загрузки файла. Telegram polling этот header
не посылает. Отрицательные synthetic update IDs не меняют checkpoint Telegram.

Каталог содержит manifest для повторного запуска того же измерения, `report.json` с
каждой HTTP-попыткой и snapshot тарифов, `report.md` с таблицей. Повтор с тем же `--output`
продолжает операции; новый каталог начинает новое измерение. Для одного каталога запускайте только один процесс benchmark одновременно. Скрипт проверяет доменные
результаты, не только status done. Report со status failed нельзя выдавать за успешную
демонстрацию. При неизвестных метриках показывается неполная стоимость, валюты суммируются
отдельно; retries включены. При новом измерении обновите таблицу выше данными успешного реального report.md и приложите дату/revision/ставки. Отчёт не содержит секретов или содержимого приватных PDF.
