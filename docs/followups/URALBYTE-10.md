# URALBYTE-10: намерение сохранить память определяет LLM

[Тикет](https://tracker.yandex.ru/URALBYTE-10) уточняет поведение согласованного
agent runtime: сообщение пользователя → LLM выбирает инструменты → backend
проверяет и выполняет вызовы → результаты возвращаются LLM → ответ пользователю.
Это отдельная доработка; вердикт клиентской приёмки и статус URALBYTE-9 не меняются.

## Подтверждённая причина

На сообщение «Привет! Запомни: меня зовут Вова.» модель вызвала `save_memory`,
но `SaveMemory.prepare/apply` повторно определяли намерение регулярным выражением,
привязанным к началу текста. Приветствие не проходило проверку. Backend вернул
canonical `needs_clarification`, которое заменило ответ LLM. Память не сохранялась,
embedding не вызывался. Это не ошибка определения намерения самой моделью.

Реальная операция `a22b972e-bdc9-4312-aa08-c86ea8dbd5f4` принята
2026-10-05 06:24:16.544299 UTC; отказ доставлен с первой попытки,
Telegram ACK 06:24:18.929592 UTC. Оба generation вызова успешны, 1536 и 1628 мс.
Проверка БД выполнялась read-only; исходный текст и Telegram ID не публикуются.
[Обезличенная диагностика](../measurements/2026-10-05-uralbyte10-before.json).

## Критерии исправления

- Намерение сохранить память определяет основной agent LLM, без regex/keyword
  gate и без отдельного предварительного классификатора.
- Приветствия, вежливые вводные и семантические варианты просьбы поддерживаются.
  Отрицание, цитата-пример и инструкции внутри PDF/результатов поиска не становятся
  просьбой сохранить память; модель получает соответствующие инструкции.
- Backend продолжает проверять разрешённые инструменты, schemas, owner, provenance,
  idempotency, leases, deadline и границы удаления. Опасные действия требуют прежнего
  immutable approval и настоящего подтверждения владельца.
- `save_memory` возвращает фактический результат в LLM; пользователь получает её
  итоговый ответ, без отдельного canonical сообщения о сохранении.
- Подтверждённая очистка памяти отсекает потенциальные отложенные записи независимо
  от формулировки исходного запроса; поздний AI/tool результат не восстанавливает данные.
- Независимые Checker и Reviewer проверяют новые сценарии и отсутствие регрессий.
  Реальные Yandex вызовы проверяются отдельно в изолированной БД с тестовым владельцем;
  synthetic production updates и подтверждения удаления не используются.

## Состояние

Базовый commit `34e52250ea6b9f218ea3ee107659e451ceb6d6cb`, ветка
`codex/memory-intent-llm`. Planner подготовил план без продуктовых вопросов;
независимый Plan Challenger APPROVE получен в первом раунде.

Первый кандидат: авторский полный набор 315 PASS и целевые 246 PASS, Ruff/diff PASS.
Независимый Checker также получил 315 PASS и проверил настоящий Yandex corpus:
10 из 11 сценариев прошли, исходный пример в JSON mode выявил BLOCKING.
Факт сохранён, но после первого generation и tool result оставшегося input budget
не хватило даже для минимальной проекции и финальной generation. Это воспроизведено
повторным реальным вызовом; нельзя выдавать успешную запись за завершённый ответ.

Первый цикл исправлений уменьшил размер JSON-инструкции без изменения её схем,
сохранил в истории проверенный вызов вместо лишней сырой оболочки ответа провайдера
и гарантировал полный UUID записи в результате для модели. Лимиты не увеличены;
canonical ответ и дополнительный classifier не введены.

Очистка памяти также сохраняет запрет на позднюю запись для всех операций из
immutable snapshot. Для ранее исполненных approvals без нового маркера используется
проверенное историческое подтверждение с тем же владельцем и payload hash.
Pending/cancelled approvals, удаление только документов и новые операции после
подготовки карточки не получают такого запрета.

Свежий независимый Checker: **325 автотестов PASS**, **11 собственных проверок PASS**,
**4/4 настоящих Yandex сценария PASS** на source freeze 2026-10-05 07:47:32 UTC.
Исходная просьба прошла native и JSON; семантическая просьба после контекста прошла
JSON, отрицание не создало записи. Во всех положительных случаях модель получила
фактический status и полный UUID, сформировала один итоговый ответ; отдельный
последующий поиск вернул сохранённый факт. Сохранение заняло 4,946–6,119 с в
изолированной тестовой среде, без учёта Telegram. JSON original использовал 15 007
единиц консервативного input budget из 16 000; это не число фактических API tokens.

Исторический corpus 10/11 относится к первому кандидату; он не выдаётся за повторный
запуск на исправленной версии. Свежие результаты закрыли фактический JSON FAIL.
Независимый **Reviewer APPROVE**: проверены фактический diff, границы разрешений,
immutable approval, повторы и JSON-протокол; два собственных adversarial теста PASS.
[Свежие измерения Yandex](../measurements/2026-10-05-uralbyte10-live-yandex.json)
содержат фактические токены, latency и сохранённые оценки стоимости. Применённые
pricing snapshots и полнота этих оценок не были экспортированы до сброса
изолированной БД; они не объявляются известными или полными.
