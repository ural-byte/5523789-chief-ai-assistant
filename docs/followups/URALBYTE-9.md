# URALBYTE-9: конфликт памяти и конечный ответ

[Blocking bug](https://tracker.yandex.ru/URALBYTE-9) продолжает клиентскую приёмку
[эпика 3](https://tracker.yandex.ru/URALBYTE-3), отдельно от URALBYTE-8.
До повторной проверки дефект блокирует демонстрацию потенциальному заказчику.
Общий клиентский вердикт остаётся PENDING.

## Фактическая диагностика до исправления

На executable `d39e998` настоящая операция `29f20a30-4cb8-4be7-8ae2-dc5d88ed0ebe`
принята 17:19:54,235 UTC, обработка началась 17:19:54,995 и завершилась
17:20:01,844 UTC. Generation 1310 + embedding 54 + generation 5144 мс — все успешные
HTTP-вызовы. Job завершён при первой попытке; snapshot pg_stat_activity не содержит
блокирующих PID. После этого final outbox остаётся pending с восемью неудачными попытками.
Progress доставлен в 17:20:07,192 UTC.

Final содержит два whitespace-символа, ноль символов после strip. Backend принимает
такой final как done; enqueue_text также принимает whitespace. Настоящий Telegram
проверочный запрос с этим невалидным текстом получил HTTP400:
«Bad Request: text must be non-empty». Ошибка сводится к общему telegram_send_failed,
повторы не имеют конечного ограничения. Это подтверждённая причина видимого зависания;
добавление только AI timeout её не устраняет.

Selective approval не создавался: разрешён только поиск, а общий инструмент удаления
покрывает полную очистку. В предыдущем ACKed ответе модель увидела текстовый конфликт,
но structured conflicts пуст: две записи извлечены, факты представлены разными
entity/predicate. У старой записи два факта, поэтому число фактов само по себе не
доказывает наличие несвязанных сведений. Исправление должно поддержать реальный сценарий,
а не только искусственный pair с одинаковыми structured keys.

Read-only проверка реальной пары выявила ещё одну особенность: старая запись содержит
обёртку атрибуции «[субъект] сообщил: «[утверждение]».». Эта обёртка не является
самостоятельным фактом. Проверка выборочного удаления должна разбирать её целиком,
сверять известного субъекта и все структурированные факты, а при дополнительных
независимых сведениях запрашивать уточнение. Содержание пользовательских записей
в отчёте не публикуется.

[Read-only проверка замороженных функций на реальной паре](../measurements/2026-10-05-uralbyte9-source-compatibility.json)
успешна. Она не создаёт approval, не удаляет память и не заменяет проверку настоящего
Telegram flow после развёртывания.

[Обезличенные метрики диагностики](../measurements/2026-10-04-uralbyte9-before.json).
Сырые finish_reason не сохранялись; исчерпание output budget не утверждается
(последний вызов сообщил 607 output, включая 479 reasoning tokens).

## Требования к исправлению

Выбор актуальной версии должен готовить точное общее destructive approval: какая запись
будет удалена/деактивирована, какая останется; owner/chat, immutable snapshot, TTL,
cancel без изменения данных и идемпотентный confirm. После выполнения retrieval
возвращает актуальную версию без повторного конфликта. Нельзя затрагивать чужие записи,
несвязанные факты или новые данные вне согласованного снимка.

Каждая пользовательская операция получает конечный исход и непустой конечный ответ:
success, clarification, waiting approval, cancelled либо explicit error. Нужны сохранённый
deadline, независимое обнаружение зависшего AI/tool/job/DB, запрет поздних результатов,
bounded retries и обработка permanent Telegram rejection. Уже зависший outbox нужно
безопасно восстановить без повторных доменных действий. Причина и operation ID остаются
в логах; пользователь видит понятное сообщение.

Обычный цикл новой задачи: Planner → Plan Challenger → Hardworker → независимый
Checker → Reviewer. Новые source/live вердикты обязательны; прежний APPROVE задачи 8
не заменяет их. Checker проверяет настоящий Telegram flow на тех же записях,
подтверждение удаления нажимает владелец. Автоматическое подтверждение не допускается.

## Согласованные инженерные ограничения

Независимый Plan Challenger APPROVE получен во втором раунде. План сохранён в тикете;
это разрешение на реализацию, а не результат проверки готового исправления.

- Выбор опирается на ранее показанный пользователю retrieval-context и точные снимки
  записей/всех фактов. Перед confirm снимок проверяется повторно. Неточное соответствие
  или изменение записи требует уточнения либо новой карточки.
- Используется общий action kind `memory_resolution`. Payload содержит ссылки и hashes;
  пользовательский текст карточки хранится отдельно и удаляется после исполнения.
  Неизвестный action kind не выполняется как встреча по умолчанию.
- Подтверждение удаляет только согласованную устаревшую запись и её копии в истории,
  cached retrieval и ожидающих карточках. Актуальная запись, новые данные, документы,
  поручения и чужие записи сохраняются. Опоздавший producer не восстанавливает удалённое.
- Сохранённый processing deadline: 90 секунд для обычных запросов и callback,
  15 минут для PDF. Это предел обработки от принятия операции, а не заявленный SLA.
  Независимый supervisor обнаруживает зависший executor; scheduler и уже подтверждённая
  уборка данных продолжают работу до истечения этого предела.
- Доставка имеет отдельный предел 60 секунд и не более четырёх попыток. Permanent
  Telegram rejection не повторяется бесконечно. Допускается единственное сообщение
  восстановления с собственным ограниченным бюджетом, без повторного запуска tools.
  Недоступность Telegram фиксируется как delivery failure; ACK не подменяется успехом.
- Ранее завершённая операция с blank final исправляется без повторения модели,
  удаления записей либо других доменных действий. Сохраняются фактические AI-метрики.
